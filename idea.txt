2. Complete workflow
We will implement this lifecycle:
1. Gymnasium initializes the simulation: creates a SimPy environment and Broker.
2. Broker registers QNodes: each QNode represents a quantum computing resource with its own capacity and backend characteristics.
3. QTasks enter the Broker: tasks are submitted to the pending queue.
4. Gymnasium receives an observation: the observation describes pending tasks and available QNode resources.
5. Scheduler selects an action: later, your RL scheduler will select which task should execute on which QNode.
6. Broker validates the assignment: checks qubit capacity, node availability rules, and task compatibility.
7. Broker dispatches the QTask: the corresponding SimPy process requests the QNode resource.
8. SimPy advances simulation time: tasks wait for resources and execute for their configured simulated duration.
9. QNode completes the task: its state and execution information are updated.
10. Broker returns execution information: Gymnasium receives the updated task and resource states.
11. Gymnasium calculates reward: the scheduler receives feedback and selects its next action.


Excellent. Then we will design QCloudRL as a complete scheduling and resource-management framework for heterogeneous quantum clouds.

Your research objective is not simply to select the best QNode for a task. It is to determine:
Given a set of pending quantum tasks and a heterogeneous collection of QNodes, which task should be executed, on which QNode, and in what order to optimize overall cloud performance?

This means the scheduler controls the complete scheduling decision:
1. Select a QTask from the ready-task queue.
2. Identify QNodes compatible with that task.
3. Evaluate the resource characteristics of those QNodes.
4. Select the most appropriate QNode.
5. Submit the task-node assignment to the Broker.
6. Let SimPy manage resource requests, waiting, and execution.
7. Observe the updated system state and make the next decision.

An important distinction: task selection and resource selection are two parts of one scheduling decision. We should not implement them as unrelated algorithms that can produce incompatible decisions.
2. How we will represent a scheduling action
For example, suppose the cloud has four QNodes and three ready tasks:

Ready tasks
Task	Required qubits	Shots
QT001	5	1024
QT002	20	2048
QT003	15	1024

Quantum resources
QNode	Backend	Qubit capacity
node_0	Washington	127
node_1	Kolkata	27
node_2	Hanoi	27
node_3	Guadalupe	16

The scheduler should select a task-node pair.

For example:
- QT001 → node_3
- QT002 → node_1
- QT003 → node_2
The scheduler must never select an incompatible task-node pair.

For RL, we can encode a scheduling action as:
\[
a = task\_index \times N_{nodes}+node\_index
\]

With 25 task slots and four QNodes:
\[
|\mathcal{A}|=25\times4=100
\]

We will use action masking so the RL agent cannot select unavailable, incompatible, or not-yet-arrived task-node combinations.
